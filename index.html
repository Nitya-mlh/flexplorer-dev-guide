The Three Tabs

Flexplorer has three distinct views. Each tab is backed by a different data pipeline. Click each card to explore.

📊
Investment Cases
Forward-looking. Shows how much revenue a modelled battery would earn under Aurora's price scenarios. Backed by Chronos simulations. Chart data is generated on-demand via ESDOS.
flex-microservice ESDOS S3
📅
Backcast Benchmarks
Backward-looking. Shows how a modelled battery would have performed historically. Month-by-month sliced simulation data. Published by Aurora analysts.
flex-microservice ESDS ESDOS
🔴
Real Performance
Real metered data. Shows how actual batteries in the market are performing — rankings, cashflow, volume. No Chronos involved. EOS pipeline feeds parquet files to DuckDB.
eos-data-uploader S3 Parquet DuckDB
Mental model: Tabs 1 & 2 are powered by the Chronos dispatch model — Aurora simulates what a battery earns. Tab 3 is powered by EOS — real metered data from actual batteries. The flex-explorer-microservice is the single API that serves all three tabs.
Concepts

Core Concepts

The entities that power Flexplorer, how they differ, how they connect — and how the data model is evolving from V3 to V4.

The Six Entities
🔬
Simulation
The atomic unit. A single Chronos model run. For backcasting it covers exactly one calendar month (to prevent the optimizer having foresight over future months). For Investment Cases it spans multiple years.

Lives in ESDS. Must always belong to a Project (project_id NOT NULL FK). Produces site_out_monthly/daily/yearly.csv.
ESDS owns Internal only
📁
Project
A container for simulations inside ESDS. Groups related runs together — e.g., all simulations for a quarterly FLEX cycle in a given region. Has a title, description, team, and tenant.

Every simulation currently requires a project_id. This is the constraint that the V4 design will relax to support asset-specific backcasting.
ESDS owns Internal only
⏪
Backcast
A collection of monthly simulations run against historical market prices. Its objective is to show what a standardized battery would theoretically have earned in past months, and to calibrate Chronos against what actually happened.

Lives in ESDS. Linked to simulations via the backcast_simulations join table. Also FK'd to a Project.
ESDS owns Internal only
📊
Benchmark
The client-visible published container in flex-microservice. Wraps N monthly simulations and exposes them as a single named product — "GBR 2hr Standard Benchmark". Has Draft → Published → Retired lifecycle.

Linked to simulations via benchmarks_metadata (stores simulation_uuid as an opaque string — no DB-level FK across services).
flex-microservice owns Client-visible
📈
FlexScenario
A grouping of Investment Cases by region, sensitivity, and PRMF cycle — e.g., "GBR Central Flex Cycle 3". Published quarterly by Research.

Think of it as the "folder" for forward-looking forecasts. Has the same Draft → Published → Retired lifecycle as a Benchmark.
flex-microservice owns Client-visible
🔋
InvestmentCase
One battery asset configuration (duration, power, site, technology) modelled as a single ESDS simulation. Belongs to a FlexScenario. Covers multiple years.

Stores simulation_uuid as a cross-service opaque reference to ESDS. The config JSON contains priceZone, forecast_start/end, and Chronos site parameters.
flex-microservice owns Client-visible

⚠ Cross-service simulation references — investment_cases.simulation_uuid and benchmarks_metadata.simulation_uuid both point to ESDS simulations but have no database-level foreign key. They are plain VARCHAR strings. If an ESDS simulation is deleted, flex-microservice will not know — it just gets a 404 when it tries to fetch outputs from S3.
Why Backcasts Run One Month at a Time
Chronos is a dispatch optimizer. If you ran it over 12 months of historical prices in a single pass, the optimizer would see future months' prices and use that foresight to charge/discharge differently than a real battery operator could. The result would be unrealistically high revenues — the model would "cheat".

By running exactly one calendar month per simulation, the optimizer only sees the prices within that month. This matches the information a real operator would have had at the time, making the backcast a fair representation of achievable performance.
V3 → V4: How the Data Model Is Evolving
Your colleague's exact point: "simulation is linked to a project — for asset-specific backcasting, we want simulation linked to a backcast."
V3 — Current State (Per-Region)
Every simulation has project_id NOT NULL.
Backcasts also FK to projects.
Backcasts reference simulations via backcast_simulations join table.
Benchmarks are regional — Aurora's standardized battery config, same for all subscribers.

Published monthly by Research. Research owns the whole flow.
-- Today simulations.project_id NOT NULL ← hard constraint backcasts.project_id NOT NULL backcast_simulations ← join table (N:M)
V4 — Future State (Per-Asset)
Simulations will be directly linked to a backcast, not (or not only) to a project.
Asset-specific inputs: ramp rate, SoC limits, degradation, cycle limits, production profiles.
Client-specific tenant publication.
Higher update frequency (daily granularity, automated monthly runs).
API delivery for optimisers (Enspired, Terralayr, Suena, Flexpower).

Piloted: Germany Research + Entrix (Aug 2026). Expanding Q4 2026.
-- V4 direction simulations.project_id NULL ← relaxed simulations.backcast_id NOT NULL ← new FK -- Blocking files to change: -- V02__basic_tables.sql (constraint) -- simulationsRepository.ts (INSERT list) -- simulations.ts (LegacySimulationCreate type)
What changes for asset-specific backcasting
Data model changes (ESDS)
• simulations.project_id → nullable
• New simulations.backcast_id FK (nullable)
• Check constraint: must have project_id OR backcast_id (not both null)
• Migration: new Flyway V-file — never modify V02
API & flex-microservice changes
• Create simulation with backcastId instead of projectId
• Benchmark metadata needs asset config (site, technology, constraints)
• Per-client tenant isolation for outputs
• Automated monthly trigger (no manual Research step)

The UI always fetches a "latest 30 days" anchor first (GET /latest?window=30d). For longer date ranges, it fires parallel chunk queries of max 6 months each. Output Pipeline: ESDOS

ESDOS converts raw Chronos CSVs into chart-ready visualisation files. It applies 3 transforms in sequence.

The 3 Converters (applied in order)
① Basis Converter
Converts between grid (per grid MW), component (per inverter MW), and absolute (raw MWh/GBP). Set by the basis field in WorkbookConfig.
② Currency Converter
Applies inflation factors. E.g., "GBP 2024 real terms" = multiply by 1.025/yr vs base year. Uses the currency_map from WorkbookConfig.
③ Normalisation Converter
Converts absolute values → per-kW. Almost always normalisation: "kW" for Flexplorer.
The 4 SQS-Triggered Lambdas
FlexExplorerVisualisationsDFunction
← FlexExplorerVisuals-Queue · max 10 concurrent
This is Flexplorer's Lambda. Writes to Flex Explorer S3 bucket.
WorkbookDFunction
← WorkBook-Queue · max 19 concurrent · generates Excel .xlsx
QaWorkbookDFunction
← QaWorkBook-Queue · QA Excel workbooks
EnergyStorageVisualisationsDFunction
← EnergyStorageVisuals-Queue · for Chronos product (not Flex)
Output CSV format (what the chart reads)
// Row 0: headers local_year , Total Project Cashflow , DC High , FFR , Wholesale , ... // Row 1: units , GBP/kW/year , GBP/kW/year , ... // Row 2+: data (one row per year × market) 2022 , 62.4 , 18.2 , 8.1 , 12.3 , ... 2023 , 58.1 , 16.9 , 7.8 , 11.5 , ...
The UI parses this with papaparse. Row 1 (units) is stripped before charting. Each column = one market segment = one stacked bar layer.

Key Queue Behaviours
⏱ Visibility timeout = 900s. If ESDOS crashes, the message reappears after 15 min for retry.
🔁 maxReceiveCount = 5. After 5 failed attempts → message goes to DLQ. CloudWatch alarm fires on any DLQ message.
🗑 ESDOS failure handling: for known non-retryable errors (e.g. LegacyWorkbookNotSupported), ESDOS manually deletes the SQS message before writing failure metadata.json. This prevents DLQ clutter.
📋 FIFO queue: The ecs-events.fifo queue preserves order and deduplicates ECS state changes — critical for the simulation state machine.

End-to-End: Publishing a Backcast Benchmark

Step through the full 5-stage journey — from the analyst's first click to a user seeing the chart.

Step 0 of 5
1
Create — POST /v1/benchmarks
Analyst fills in region, battery duration, price zone. A benchmarks DB row is created with status = 'Draft'. Nothing else happens yet — no S3 writes, no SQS.
INSERT INTO benchmarks (benchmark_uuid, region, battery_duration, status, ...) VALUES ('uuid1', 'gbr', 2, 'Draft', ...)
2
Add Data — PUT /v1/benchmarks/{id}/add
Analyst picks completed Chronos simulation(s). For a 36-month benchmark, this triggers:
  • Copy full site_out_*.csv from ESDS bucket → Flex Explorer bucket
  • Slice month-by-month (36 months × trim to exact date range)
  • Write monthly + daily WorkbookConfigs (72 config.json files)
  • Send 72 SQS messages to FlexExplorerVisuals-Queue
  • Insert benchmarks_metadata rows into DB
3
ESDOS Processes (async, ~5–10 min)
Up to 10 concurrent FlexExplorerVisualisationsDFunction Lambda invocations run in parallel. For each message:
  • Reads config.json from S3
  • Reads trimmed site_out_monthly.csv
  • Applies 3 converters: Basis → Currency → Normalisation
  • Writes visualisation-external-{uuid}.csv to S3
  • Writes metadata.json {"status":"success"}
4
Publish — PATCH /v1/benchmarks/{id}/status
Analyst clicks "Publish" in the UI. The API validates that metadata entries exist, then:
UPDATE benchmarks SET status = 'Published', published_at = NOW() WHERE benchmark_uuid = 'uuid1'
Benchmark is now visible to all users with access to that region.
5
User Views Chart — GET /v1/benchmarks/{id}/data/internal
The flex-microservice:
  • Reads latest_release_month from DB
  • Fetches each month's visualisation-external-{uuid}.csv from S3
  • Concatenates 36 monthly CSVs (strips units row from all but the last)
  • Streams the combined CSV to the browser
Browser parses with papaparse → Highcharts bar chart rendered! ✓
Reference

Glossary

Chronos
Aurora's energy storage dispatch model (Python). Simulates battery revenue year by year using market prices and asset parameters.
ESDS
energy-storage-dispatch-service. The orchestrator — manages simulation lifecycle, exposes the main API, launches ECS tasks.
ESDMR
energy-storage-dispatch-model-runner. The Docker container on ECS Fargate that actually runs the Chronos model.
ESDOS
energy-storage-dispatch-output-service. Converts raw simulation CSVs into chart-ready visualisation CSVs and Excel workbooks.
EOS
Energy Operations System. The real-data platform covering metered battery performance. Powers the Leaderboards tab.
FlexScenario
A named Aurora price scenario grouping related Investment Cases (e.g., "GBR Central Flex Cycle 3"). Has region, sensitivity, flex cycle.
InvestmentCase
A specific asset config (duration, power, site) modelled as one Chronos simulation within a FlexScenario.
Benchmark
A published set of backcast simulations covering a historic time period. Each month is independently processed by ESDOS.
WorkbookConfig
JSON uploaded to S3 before sending an SQS message. Tells ESDOS what to generate: output_format, simulations, currency_map, basis, normalisation.
workbook_storage_location
The S3 prefix carried in every SQS message. ESDOS reads config.json from here and writes results back to the same prefix.
Processing Loop
Lambda that runs every 15 minutes. Submits ECS tasks for simulations ready to advance to the next state. The heartbeat of the system.
DuckDB
In-process SQL engine used in flex-microservice Lambdas. Queries S3 parquet files directly without loading data into memory. Powers the Leaderboards tab.
Basis
How simulation outputs are normalised: grid (per grid MW), component (per inverter MW), absolute (raw MWh/GBP values).
Universe
Deployment environment: production, staging, development. All bucket names, SSM paths, and queue names include it.
flex-unit-breakdown
The data type written by eos-data-uploader that powers the Leaderboards tab. One row per battery per day, with cashflow and volume breakdown.
chartMapping.csv
Config file at S3 that maps internal market codes to display names and ordering in charts. Read by ESDOS when generating vis CSVs.
Origin
Aurora's scenario explorer platform. Market scenarios are published here first, then the OriginIntegrationFunction copies them to ESDS via SNS → SQS.
tsoa
TypeScript OpenAPI framework. Routes in ESDS and flex-microservice are generated from controller decorators — not hand-written in Express.
Flyway
Database migration tool. Runs versioned SQL files (V01__, V02__...) to evolve the MySQL schema. Never modify old migrations — always add new ones.
DLQ (Dead Letter Queue)
Every SQS queue has a DLQ. After 5 failed attempts, the message goes there. A CloudWatch alarm fires on any DLQ message — this is your signal that something silently failed.
